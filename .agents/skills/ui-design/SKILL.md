# UI 设计与审查

把项目自身的设计语言转为可执行改动与检查，不套用固定品牌外观，不替代产品需求、业务授权或人工视觉验收。

## 1. 确认任务和输入

- 区分设计方案、实现修改、只读审查；只读审查不修改文件，方案不自动进入实现。
- 输入可为需求文字、截图、组件源码、参考链接或已有 DESIGN.md。只问会实质改变结果的缺失信息；能从项目确认的不要反复询问。
- 在用户授权且资料可用的范围内，先读仓库规则、产品需求、设计标准与相关组件，再查实际令牌、主题入口、构建链及测试。仅截图或限定文件审查时不额外探索项目，缺失信息标为假设或未验证。截图只能证明可见外观，不能证明点击、持久化或业务成功。
- 输出任务范围、规范来源、现状偏差、可改文件和验证条件。没有源码时给明确标注假设的方案，不编造路径、令牌或已完成事实。

## 2. 形成最小充分方案

读取 references/design-principles.md，把规则映射到项目已有令牌与组件。项目明确需求和设计标准优先；源码用于核实现状，不把既有缺陷当规范。发生实质冲突时说明并确认，不静默选边。

- 为目标组件列出适用状态：空态、等待、进行中、成功、错误、禁用、折叠、展开及只读。
- 定义信息层级、内容宽度、对齐、间距和窄容器行为；复用已有组件与语义令牌，不平行建立第二套设计系统。
- 新语义确有必要时，在现有令牌层最小扩展，同时考虑亮暗主题；不为单个组件大范围重构。
- 参考站点仅提炼原则。记录来源及固定版本；版本未核实就标注未固定，不复制品牌资产、专有字体或整页布局。

## 3. 按授权实施或审查

- 实现只处理用户目标；保持现有框架、运行时、CSP、离线资源和构建约束。不默认安装组件库、字体、浏览器或其他依赖。
- 折叠图标保留可读名称、键盘操作与展开状态；等待反馈可被辅助技术读取；提交后展示真实回执而非先报成功。
- UI 状态不得伪造业务授权、执行完成或保存成功。越出渲染边界的需求单独说明，不顺手修改权限、协议、取消、结算或持久化逻辑。
- 审查按严重度报告文件位置、实际证据、用户影响与最小修复建议；推测与已复现问题分开。

## 4. 分层验证

读取 references/verification.md，按项目真实命令验证，不把文件名或 npm 脚本示例当作已存在能力。

1. 检查差异、相关测试和构建约束；只运行当前任务需要且已获授权的命令。
2. 有 GUI 工具时检查实际目标入口、亮暗主题、宽窄容器、长文本、键盘与减少动画；截图不能代替交互验证。
3. 工具缺失或启动失败时记录限制，不关闭沙箱、不降低安全、不将跳过记为通过。
4. 区分源码、单测、隔离页面、真实应用和打包态证据。未经实际检查，不宣称可访问性合规、视觉验收或版本交付完成。

## 5. 输出结果

简明汇报：任务模式与范围；设计依据和令牌映射；变更或问题清单；实际执行的验证及结果；未验证边界与下一步。设计建议不冒充已实现，自动检查不冒充用户认可。

## 资源与使用边界

- references/design-principles.md：通用原则、令牌映射和组件状态检查。
- references/verification.md：验证矩阵、审查输出和证据分层。
- 运行依赖：能读取项目文件的 AI 助手；修改需要文件编辑能力，自动测试需要项目既有工具，视觉检查需要可用 GUI/截图能力。Skill 本身不安装依赖、不联网抓取资料、不自动执行代码或发布。
- 不适用：原生移动端专属组件规范、CLI TUI、后端业务实现、品牌资产仿制、无工具证据的合规认证。遇到这些任务说明边界或转交相应能力。
