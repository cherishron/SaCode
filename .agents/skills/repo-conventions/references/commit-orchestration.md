# M. 提交编排与推送（Commit Orchestration）

目的：解决**长期不提交、改动越攒越多、功能互相覆盖、想提交又不敢**的痛点。把一堆未提交改动——**先与远端同步、解决冲突**，再**按功能自动拆成干净提交**，最后**用户确认后推送**。

## 核心前提：先同步，再提交（rebase 优先）

**不要**在落后的本地直接堆提交。顺序固定为：

1. **把未提交改动暂存**（`git stash`，含未跟踪需显式带上），让工作区干净。
2. **拉取远端**（`git fetch`）→ 判断本地落后 / 分叉。
3. **变基到远端最新**（`git rebase`），**先解决冲突**。
4. **恢复改动**（`git stash pop`）——此时可能再出一批冲突（本地改动与已更新的文件冲突），**逐个解决**。
5. 解决后**跑相关测试**，确认没被同步打破。

只有走完 1–5，才进入"按功能提交"。

## 工作流

| 步骤 | 做什么 | 谁做 |
|---|---|---|
| 盘点 | `git status` + diff 分级，列出**全部未提交改动** | AI 自主 |
| 聚类 | 把改动**按功能主题**分组，标注每组"疑似完成 / 在飞半成品" | AI 自主 |
| 定边界 | **判定哪些功能已完成、可提交**（在飞的不提交） | AI 自主 |
| 同步 | 上述"先同步再提交"五步，**解决冲突** | AI 自主，解不了才停 |
| 提交 | 按主题**精确 add**，一条主题一条提交 | AI 自主 |
| 推送 | 列出**将推送的提交**，用户点头后 `push` | **人工卡点** |

## 自动 vs 人工（本领域的核心约定）

- **AI 自主完成**：盘点、聚类、判定完成边界、生成提交、冲突 rebase 与常见冲突解决。
- **人工卡点**：**仅在推送前**——列出将要推送的提交清单，用户确认后才 `push`。
- **例外**：冲突**无法自动解决**（语义冲突、需业务取舍）时，**停下**说明冲突点并给可选方案，不硬猜。

> 判定完成边界由 AI 做，正是本领域价值所在——否则退化成手动 git，失去意义。但**推送**这个不可逆外发动作，始终保留人工二次确认。

## 红线（继承仓库提交规约）

- **禁 `git add -A` / `git add .`**；只按文件路径**精确 add**。
- 提交前查**密钥 / 产物**：真实凭据、构建产物、日志不得入库（呼应 D 领域）。
- **不提交他人 / 其他会话的在飞实现**。
- **不 force push、不改写已推送历史**（除非用户明确授权）。
- message 中文，`feat(scope): 描述`（scope 用模块名）。

## 输出

- **提交计划**：未提交改动 → 功能分组 → 每条提交的 message + 文件清单。
- **同步记录**：rebase 过程、冲突点与解决方式。
- **推送清单**：待用户确认的提交（含目标分支 / 远端）。

## 边界

- 提交 / 推送须用户授权；本领域默认**推送前确认**。
- 无法判定归属的模糊改动：归入"**待确认、暂不提交**"，**不硬塞**进任何一条提交。
- 抽样盘点不等于覆盖全部改动，未盘到的须写明。
