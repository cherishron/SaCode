# A. 项目结构规范

目标：让"每个东西只有一处正确位置"，别人一眼知道去哪找、改哪个。

## 检查项

- **单入口**：核心源码、桌面/前端源码、CLI 各有且只有一个源码位置；无"空壳目录"冒充实现。
- **模块边界**：每个顶层目录职责单一、命名与职责相符；共享核心与各入口的依赖方向清晰（入口依赖核心，核心不反向依赖入口）。
- **顶层目录白名单**：仓库根只放源码、文档、配置、脚本、测试与已有约定目录；**不放**临时产物、私有副本、日志、快照、数据集。
- **构建产物**：产物目录（`dist/`、`target/`、`node_modules/`、`build/`）在 `.gitignore` 中，不入库。
- **命名一致**：目录/文件/包命名风格统一（如小写连字符），无同一概念多名。

## 常见问题

- 根目录散落未跟踪、未忽略的临时目录或文件（最高频）。
- 双入口或重复真源（同一能力两处实现/两处配置）。
- 测试与源码混放且无约定，或测试产物混入源码树。
- 目录名与职责不符（凭目录名猜模块边界最容易出错）。

## 输出

1. **目录职责表**：路径 / 职责 / 是否合规。
2. **问题分级**：每条给位置与证据。
3. **是否该整理的结论**：该整理的给"最小整理集 + 影响面 + 风险"；**不擅自搬目录**，搬动须用户确认。

## 边界

- 只读判断优先；整理与重命名属高风险，须单独授权。
- 不因为"看起来乱"就大搬；先问"这样改是否值得、影响哪些引用"。
