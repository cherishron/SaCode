# K. 项目评审（代码 / 架构 / 质量 / 治理）

目的：做一次**结构化评审**，产出分级发现与建议。**只读优先，不替用户改代码**——发现整改交由用户/agent 按授权执行。

## 方法

1. **先声明评审范围、方法与局限**：是**抽样**还是**全量**？有没有真跑构建/测试？有没有做安全渗透？**未覆盖的部分要写明**，不能默认"看过就是全过"。
2. **四个维度**：
   - **架构**：模块边界清晰吗？依赖方向对吗（核心不反向依赖上层）？是否单一真源？是否有绕过主干的旁路？
   - **代码质量**：复杂度、命名、重复、死代码、可测性、异常/错误是否 fail-loud。
   - **测试**：覆盖关键路径吗？测试**可跑**吗（能不能真的跑起来）？口径是否与验收一致？有没有"假通过"（假模型夹具 / 断言式自测冒充真实任务）。
   - **治理**：进度是否如实登记？文档是否与实现同步？协作机制是否运转（多人是否按登记机制走）？
3. **分级发现**：每条给 **P0 / P1 / P2** + **证据路径**（文件:行）+ **最小修复建议**。
   - P0 = 阻断正确性 / 安全性 / 可用性的硬缺陷
   - P1 = 重要但非即时阻断（如基线缺失、关键单测跑不起来）
   - P2 = 硬化 / 改进项

## 输出

**评审报告**：总体结论 + 分级发现表 + 修复清单 + 明确标注的未覆盖项。

## 边界

- **抽样 ≠ 全量**，必须在报告里写明，不把抽样结论当整体结论。
- **不擅自重构 / 提交**；任何改动须授权。
- 发现即记录（证据路径），不凭印象下结论。
