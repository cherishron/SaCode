# SaCode 项目结构审查报告

> 审查日期：2026-10-01 · 审查方式：全量目录扫描 + crate 依赖图 + 模块职责抽样核实
> 范围：仓库整体（Rust workspace + TS 前端 + 文档 + 脚本 + 工程配置）

## 一、总体结论

**局部微调足够，不需要大重构。**

判断依据：
1. **crate 级依赖图清晰单向**：`kernel`（零内部依赖）← `runtime`（+`acp-client`）← `cli` / `acp` / `lsp`；`acp-client` 完全独立；`desktop` 无任何内部 path 依赖（经 sidecar 二进制集成，边界最干净）。Cargo 机制保证 crate 级无循环依赖，实际检查也未见异常边。
2. **分层职责基本正确**：kernel 5,955 行精炼内核；runtime 承载运行时域；interfaces 承载用户入口；client-core 作为 TS 共享库被 desktop 消费，方向正确。
3. **命名大体一致**：Rust 侧 snake_case 模块、TS/npm 侧 kebab-case、docs/ 已按 `<类型>-<主题>.md` 规范化重整（断链 0）。
4. 问题集中在两类——**双实现漂移**与 **runtime god-crate 趋势**——均可用局部微调处理；唯一有重构性质的选项（拆分 runtime）建议**推迟**（理由见 P2-4）。

## 三、问题清单（分级）

### P1 · ACP 协议双实现且已漂移（应尽快修，属局部微调）

**证据**：
- `interfaces/acp`（服务端）讲 **ACP v1 规范**：流式通知用 `session/update`（本轮 ebaf321 刚改造对齐）。
- `integrations/acp`（客户端）讲 **opencode 旧方言**：`METHOD_SESSION_EVENT = "session/event"`、`session/permission`、`session/permission/resolved`。
- 两个 crate 各自完整实现一套 JSON-RPC 信封：服务端 `JsonRpcRequest/Response/Error/Notification`（382 行 protocol.rs），客户端 `JsonRpcId/Error/Request/Notification/Response/Message`（244 行 protocol.rs）。**626 行协议代码近半重复**。

**风险**：外部 agent（opencode/codebuddy/qoder）持续向 ACP v1 演进，客户端方言将收不到 `session/update` 流式事件；两处协议类型各自改动必然继续漂移。这正是"同一协议、两个真源"的典型结构病。

**建议**：抽 `acp-protocol` 共享 crate（JSON-RPC 信封 + 方法常量 + ACP v1 消息类型），`sacode-acp` 与 `sacode-acp-client` 均改为依赖它；客户端对 opencode 方言的兼容（`session/event` 等）收敛到 `opencode_map.rs` 一处映射层。**动作量：新增 1 个小 crate + 两处 import 调整，不动整体目录布局。**

### P2 · 择机修（局部微调可解决）

**P2-1 providers.json 双写方（职责重叠）**
- 证据：`interfaces/cli/src/provider_config.rs`（1,067 行）读写 `~/.sacode/providers.json`；`runtime/src/daemon/providers.rs` 也读写同一文件（insert_provider_config/remove_provider_config）。同一持久化状态、两个 crate 各持一套读写逻辑。
- 建议：确立单一事实源——provider 配置读写统一下沉 runtime（类型已在 kernel::model），CLI 只做展示/调用层。
- 理由：双写方对同一 JSON 的 schema 演进必然失同步，且已观察到 config.json 结构在两侧不一致的苗头。

**P2-2 模型路由双模块（命名撞车）**
- 证据：`runtime/src/model_routing/`（任务画像路由：TaskProfile/ModelRoutePlan）与 `runtime/src/agents/model_router.rs`（角色模型路由）——两个"灵枢·自愈合"路由模块，从名字无法判断改哪个。
- 建议：合并为一处，或改名显式区分（如 `task_routing` vs `role_routing`）。

**P2-3 vite.config.ts 死路径**
- 证据：`interfaces/desktop/vite.config.ts` 的 sidecar 二进制首选路径 `saaiRoot/SaCode/target/debug/sacode.exe`——**`../SaCode` 目录不存在**（已实测），全靠 fallback（workspace target）兜底。
- 建议：删除死路径，统一走 `SACODE_BINARY_PATH` → workspace target 的单一解析链。
- 理由：隐性脆弱——哪天 fallback 条件变化即静默坏掉。

**P2-4 runtime god-crate 趋势（73K 行 / 183 文件 / 28 域）—— 建议暂不拆**
- 现状：daemon/executor/queue/provider/identity/store/skills/memory/plugin/git_auth/ai_design/code_audit/agents/agent_backends/… 全在一个 crate。
- 判断：**内聚尚可**（daemon 门面 + executor/queue 协作紧密），且当前工作树有 132 文件的桌面迁移 WIP 未合入——此刻拆分必然制造大规模冲突。
- 建议：①现在只做"**冻结新增域**"——新功能优先落 kernel 或独立小 crate，不再往 runtime 加顶层域；②WIP 合入后再评估按「daemon 门面 / 核心运行时 / 外部集成」三块拆分的收益。

## 四、健康面（做得对、不要动的）

1. **kernel 极简**（6K 行、零内部依赖）——内核约束良好，是整个分层的地基。
2. **desktop 以二进制边界集成**（无 path 依赖 + sidecar spawn + token 不进 WebView）——避免了大面积耦合，Tauri 壳与 Rust 平台层可独立演进。
3. **acp-client 独立无内部依赖**——可被任何 crate 复用而不引入传递依赖。
4. **client-core 作为 TS 单一共享层**——desktop 不直接手写 daemon 协议。
5. **docs/ 已规范化**（159 链接断链 0，命名统一）。
6. **npm-package 产物已 ignore**（tgz 仅本地）、updater 私钥已 ignore。

## 五、建议执行顺序

1. **P1**：抽 `acp-protocol` 共享 crate，统一协议真源（半天级）。
2. **P2-3 + P3**：死路径 + 空目录 + gitignore + sdk 占位（半小时级，零风险）。
3. **P2-1 + P2-2**：providers.json 单一事实源 + 路由模块改名（各半天级，趁 WIP 合入后做）。
4. **P2-4**：runtime 拆分**不现在做**——先冻结新增域，WIP 合入后再立项评估。

## 六、一句话结论

结构骨架（分层/依赖/边界）是健康的，病灶在"同一职责的两套实现"（ACP 协议、provider 配置、模型路由）与 runtime 的持续膨胀——前者局部微调即可根治，后者只需纪律而非手术。**不需要大重构。**
