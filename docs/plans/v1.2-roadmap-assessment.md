## 3. 下一阶段方向分析

四维评估的 P0–P5 已全部落地，下一阶段不再由评估报告驱动，而是由**产品成熟度**和**用户增长**驱动。

### 3.1 候选方向

| 方向 | 价值 | 工作量 | 风险 |
|------|------|--------|------|
| **A. VSCode 扩展深化** | 扩大用户基数（IDE 用户 >> 终端用户），选区注入+审批可视化+diff 展示 | 中 | 低（已有 MVP 基础） |
| **B. 代码库理解质量** | 提升 code.symbols/code.deps/AST 解析准确率，增强 LLM 上下文裁剪 | 中 | 中（需要多语言测试覆盖） |
| **C. 性能优化** | 大文件解析、工具执行延迟、daemon 内存占用 | 低-中 | 低 |
| **D. 事件溯源切片 2+3** | checkpoint 快照化 + audit.log 合并 | 低 | 低 |
| **E. provider 生态扩展** | 新增 provider 预设（月之暗面、百川、MiniMax 等） | 低 | 低 |
| **F. 企业级功能** | 审批 API 外部化、RBAC、团队配置共享 | 高 | 高（需要真实企业用户验证） |
| **G. 测试覆盖率提升** | 测试仍集中在 runtime，cli/e2e 覆盖不足；不再引用无基线支撑的累计条数 | 中 | 低 |

### 3.2 推荐方向排序

**第一优先：A（VSCode 扩展深化）**

理由：
1. report-plan.md 步骤 2 明确标注"ROI 最高单项投入"
2. 当前 MVP 仅 3 个 TS 文件（~20KB），从"能用"到"好用"差距小
3. IDE 用户基数远超终端用户，是用户增长的最大杠杆
4. 不需要新的 runtime 能力——复用现有 daemon HTTP/SSE 端点

具体交付：
- 编辑器选区 → 上下文注入（选中文本自动作为 prompt 前缀）
- 审批流可视化（build 模式下在 IDE 内弹出审批面板）
- diff 内联展示（fs.edit/fs.apply_patch 的变更在编辑器内高亮）
- sacode 进程自动管理（扩展激活时自动启动 daemon）

**第二优先：G（测试覆盖率提升）**

理由：
1. v1.1 稳定化投入了大量 clippy/编译修复，但 e2e 覆盖仍然不足
2. 事件溯源切片1刚落地，需要集成测试验证投影一致性
3. 低风险、高回报——防止回归

**第三优先：D（事件溯源切片 2+3）**

理由：
1. 设计文档已就绪，实施路径清晰
2. checkpoint 快照化对 daemon 重启场景有实际价值
3. 工作量小，可作为间隙任务

### 3.3 不推荐近期投入的方向

- **F（企业级功能）**：无真实企业用户验证，容易再次过度设计
- **Scheduled Tasks / Agent Teams / Channels**：平台化收敛声明已明确延后
- **C（性能优化）**：当前无性能瓶颈报告，过早优化无目标
