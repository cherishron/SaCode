## A. 品牌与命名

### D1. 「灵枢」到底定位成什么？（最关键）
**问题**：在 UI 与代码中，用户会同时看到 `SaCode`（产品名）和 `灵枢`（「灵枢 · 角色编排」「灵枢四卡」等）。架构文档把灵枢定义为「核心技术品牌名称」，但它已直接暴露给终端用户。你希望它扮演什么角色？
**背景**：`ChatCard.vue`、`turn-events.ts` 等把灵枢作为面向用户的事件/卡片标题；`AGENTS.md`、`architecture.md` 又把它当作内部架构隐喻。双品牌并现会让用户困惑「灵枢是产品、功能还是引擎？」
**备选方案与后果**：
- **方案 A（推荐｜引擎代号）**：灵枢仅作内部架构代号，UI 文案改为中性词（「角色编排」「冲突干预」「任务摘要」），不向用户暴露。→ 改动集中在少数组件、最省事、用户心智最干净。
- **方案 B（功能/子品牌）**：灵枢作为面向用户的功能品牌保留，需明确其与 SaCode 的主从关系，并在品牌圣经中定义。→ 需额外品牌资产与文案体系，且要重新设计相关卡片标题。
- **方案 C（完全弃用）**：统一只用 SaCode，灵枢从 UI 与文档全面移除。→ 最纯净但改动面最大（涉及代码注释、文档、组件多处）。
**建议关注**：若短期目标是「尽快 Ga」，选 A；若想把灵枢作为差异化卖点，选 B 并补品牌资产。

> ✅ **已决策（2026-10-01）：方案 A — 仅内部架构代号。** 对外统一 SaCode；UI/文档中「灵枢」改为中性词（角色编排 / 冲突干预 / 任务摘要），不再向终端用户暴露。

### D2. 主色与跨端视觉基调定哪一版？
**问题**：当前存在三套互相矛盾的品牌色——VSCode 图标蓝 `#366CFF`、设计文档 GitHub 蓝 `#2f81f7`、桌面端实际落地的暖色陶土 `#d97757`。你拍板以哪一套为**唯一真源**？
**背景**：审计发现设计方向漂移（v1 蓝版 vs refresh 暖版并存），且你偏好「低调深色系」。桌面端 CSS 实际已用暖色，但 VSCode 图标与部分文档仍是蓝色。
**备选方案与后果**：
- **方案 A（推荐｜暖色陶土）**：以 `#d97757` 体系为唯一品牌色，同步重绘 VSCode 图标蓝、废弃 v1 蓝版文档。→ 契合你的偏好、与已落地实现一致；需一次性的图标/文档色值修正。
- **方案 B（GitHub 蓝）**：统一回 `#2f81f7`/`#366CFF`。→ 与已落地的暖色实现冲突，需回改桌面端，且偏离你的「低调」偏好。
- **方案 C（维持双轨）**：TUI/图标用蓝、桌面用暖。→ 跨端视觉不一致，长期维护成本高。
**建议关注**：定 A 可立即解锁图标重绘与文档收敛，是 PRD E6 的前置决策。

> ✅ **已决策（2026-10-01）：方案 A — 主色 = `#366CFF`。** 以 VSCode 图标蓝为唯一真源，废弃 `#2f81f7` 与 `#d97757`；需重绘图标、收敛文档与桌面端 CSS（PRD E6）。

### D3. 品牌标语（中英文）用哪一句？
**问题**：产品目前缺失正式的一句话价值主张，About 页与对外文案应有统一标语。你倾向什么基调？
**背景**：roadmap 现有核心叙事为「Claude Code 的体验，国内模型原生适配，企业级可审计」。
**备选方案与后果**：
- **方案 A（推荐｜沿用并精炼）**：基于现有叙事改写为中英文标语（如中文「Claude Code 的体验，国内模型原生适配」）。→ 低成本、口径一致。
- **方案 B（全新拟定）**：从零起草，强调差异化。→ 更出彩但需多轮打磨。
- **方案 C（暂不设标语）**：仅保留产品名与描述句。→ 最简，但品牌感弱。
**建议关注**：基调选「技术范」还是「商务/企业范」会决定后续所有对外文案语气。

> ✅ **已决策（2026-10-01）：以产品名 `SaCode` 为品牌核心词，标语在现有叙事上精炼（不做虚浮口号）。** 中英文文案在品牌圣经定稿；示例中文：「SaCode · Claude Code 的体验，国内模型原生适配，企业级可审计」。

- **方案 C（暂不复用）**：仅修正现有 sa-logo 颜色，不新做母版。→ 最快但资产不完整。
**建议关注**：若计划正式对外发布，商标预检建议不跳过。

## B. 桌面端发布与分发

### D5. 代码签名与公证的证书从哪来？
**问题**：要让桌面端被系统信任安装，必须做 Windows Authenticode 签名与 macOS 公证。证书/账号由谁提供？
**背景**：`tauri.conf.json` 目前 `bundle.active:false`，无 `bundle.windows`/`bundle.macOS` 配置。
**备选方案与后果**：
- **方案 A（自购证书）**：采购 Windows 代码签名证书 + 注册 Apple Developer（含公证）。→ 最规范，但有成本与采购周期，会直接影响 Ga 时间表。
- **方案 B（CI 签名服务）**：用 CI 提供商/第三方签名服务。→ 减轻本地负担，但需配置与可能的订阅费用。
- **方案 C（暂缓 macOS 公证）**：先只做 Windows 签名，macOS 以未公证/开发者自签先行。→ 可早发 Windows 版，但 macOS 用户安装受阻警。
**建议关注**：这是发布时间线的硬阻塞项，需最早确认预算与采购。

> ✅ **已决策（2026-10-01）：方案 C — 先发 Windows 版（Windows Authenticode 签名），macOS 暂缓公证（开发者自签/未公证先行）。** Windows 版可最早 Ga；macOS 安装阻警在文档中说明。

### D6. 自动更新机制要不要做、怎么做？
**问题**：当前完全无自动更新（无 updater 插件/签名更新源）。首版是否必须带自动更新？
**背景**：PRD E2 把 updater 列入 M3。
**备选方案与后果**：
- **方案 A（推荐｜tauri-plugin-updater）**：引入签名增量更新。→ 用户体验好、运维可控；需配置签名更新通道。
- **方案 B（仅发布公告手动更新）**：发版只提示用户手动下载。→ 简单，但留存与体验差。
- **方案 C（第三方更新服务）**：接入外部更新平台。→ 省心但有外部依赖与隐私考量。
**建议关注**：与 D5 签名强相关——没有签名就没有可信更新通道。

> ✅ **已决策（2026-10-01）：方案 A — tauri-plugin-updater 签名增量更新。** 已有 Windows 签名，可建可信更新通道；macOS 未公证期间更新通道仅覆盖 Windows。

### D7. 桌面端版本号怎么跟 CLI 对齐？
**问题**：CLI 已是 `1.1.1`，但桌面端 `tauri.conf.json` 仍是 `0.1.0`。发布时版本策略怎么定？
**背景**：多端版本认知一致性影响用户信任。
**备选方案与后果**：
- **方案 A（推荐｜统一版本号）**：桌面跟随 CLI 主线（如 1.5.0），与发布 PRD 对齐。→ 认知统一、便于支持。
- **方案 B（桌面独立版本线）**：桌面走自己的 0.x/1.x。→ 迭代自由，但用户易混淆。
- **方案 C（先发「预览版」）**：不等 Ga，先以预览版早发、版本独立。→ 早收集反馈，但品牌完整性不足。
**建议关注**：若选 C，需明确「预览版」与「Ga」的功能边界，避免承诺过度。

> ✅ **已决策（2026-10-01）：方案 A — 统一版本号，桌面跟随 CLI 主线（对齐发布 PRD 版本，如 1.5.0）。** 多端认知统一、便于支持。

### D8. 首版 Ga 是否纳入通知/多窗口/浅色等 P2 体验项？
**问题**：PRD M3 含通知、多窗口、窗口态持久化、浅色主题等 P2 项。首版范围你怎么切？
**背景**：这些非阻塞但影响体验完整度。
**备选方案与后果**：
- **方案 A（推荐｜最小可用 Ga）**：首版仅含 P0/P1（可安装、安全、稳定、品牌一致），P2 留待 1.5.x 迭代。→ 最快 Ga、风险最低。
- **方案 B（纳入部分 P2）**：至少含通知与窗口态持久化。→ 体验更完整，工期略增。
- **方案 C（全量）**：P0–P2 一次到位。→ 最完整，但排期拉长。
**建议关注**：结合 D17 的人力判断来定。

> ✅ **已决策（2026-10-01）：方案 C — 全量 P0–P2 一次到位。** 首版即含通知/多窗口/窗口态持久化/浅色主题等 P2 体验项；排期相应拉长，按 M1→M3 分批交付。

## C. 安全加固

### D9. 守护进程审批接口的鉴权范围？
**问题**：daemon 的 HTTP 审批接口当前鉴权待确认——若仅绑 `127.0.0.1`，本地任意进程理论上仍可代用户审批工具调用。你要求什么级别的防护？
**背景**：`runtime/src/daemon/approval.rs` 暴露审批 REST 接口，需确认是否带 token 校验。
**备选方案与后果**：
- **方案 A（推荐｜localhost + 随机 token）**：接口除绑定本机外，还需一次性随机 token 校验（token 通过 ready-file 下发）。→ 防止本地提权。
- **方案 B（仅 localhost 绑定）**：依赖网络隔离。→ 实现简单，但本地恶意进程可滥用。
- **方案 C（用户级隔离）**：按系统用户做权限隔离。→ 最强，但工程复杂。
**建议关注**：这是安全审计里的「待确认」高危项，建议优先核实现有实现再拍板。

> ✅ **已决策（2026-10-01）：方案 C — 用户级隔离（按系统用户做权限隔离）。** 最高防护级别、工程复杂度高；实现分级落地：L1 先 localhost + 一次性随机 token（token 经 ready-file 下发），L2 再叠加 OS 用户会话隔离。需先核实现有 `runtime/src/daemon/approval.rs`。

### D10. Shell 命令安全策略：黑名单、白名单还是沙箱？
**问题**：当前 shell 执行靠子串黑名单（`is_dangerous_command`），易绕过且误伤正常命令。你要换成哪种策略？
**背景**：这是面向 LLM 驱动 shell 的固有难题。
**备选方案与后果**：
- **方案 A（能力白名单）**：只放行明确允许的高级命令，其余拒绝。→ 最安全，但限制部分灵活性（如罕见命令需用户加白）。
- **方案 B（维持黑名单 + 优化）**：保留但改为更稳健的解析（避免 `sh -c` 绕过）。→ 改动小，残余绕过风险。
- **方案 C（容器/沙箱隔离）**：在隔离环境中执行 shell。→ 最强防护，但工程量与资源开销大。
**建议关注**：若短期求稳，B 可先止血；若要长期安全基线，A 是方向。

> ✅ **已决策（2026-10-01）：方案 C — 容器/沙箱隔离执行 shell。** 最强防护、工程量与资源开销大；落地分级：先 L1 稳健解析黑名单止血，L2 再引入隔离执行。与 D11 安全底线协同。

### D11. 密钥库失败时的回退底线？
**问题**：当前 keyring 写入失败会**静默回退明文落盘**。你确认的底线是？
**背景**：审计列为 P0 高危泄露。PRD E3 已建议「必须显式 `--insecure-file-secrets` 才回退」。
**备选方案与后果**：
- **方案 A（推荐｜必须显式授权才落盘）**：默认失败即报错退出，仅 `--insecure-file-secrets` 才回退明文。→ 安全底线清晰。
- **方案 B（完全禁止落盘）**：任何情况都不写明文。→ 最安全，但无头环境可能无法持久化凭据。
- **方案 C（允许但强提醒）**：回退时显著告警。→ 折中，但仍可能误落盘。
**建议关注**：此决策风险高，建议直接采用 A 并写进发布门禁。

> ✅ **已决策（2026-10-01）：方案 A — 必须显式 `--insecure-file-secrets` 才回退明文；默认 keyring 失败即报错退出。** 写入发布门禁（PRD E3）。

- **方案 B（仅能力探测）**：保持深色，但加 truecolor 探测避免失真。→ 改动小，不解决浅色需求。
- **方案 C（暂不做）**：保持现状。→ 最快，但部分用户不适。
**建议关注**：与 D2 主色解耦，可独立排期。

> ✅ **提议默认（2026-10-01，D17 自主实现采纳，可覆盖）：方案 A — 浅色主题 + truecolor 能力探测。** 与 D2 主色解耦，独立排期。

### D13. CLI 自动补全要不要、怎么做？
**问题**：CLI 完全无 shell 补全（bash/zsh/fish/pwsh）。是否引入、以何种方式？
**背景**：审计列为 Medium 减分项。
**备选方案与后果**：
- **方案 A（基于 clap 派生补全）**：重构参数解析为 clap 并自动生成补全脚本。→ 补全完善，但需改现有自研 `arg_parser`。
- **方案 B（手写补全脚本）**：不改解析器，提供脚本。→ 快但维护弱。
- **方案 C（暂不做）**：留待后续。→ 不影响 Ga。
**建议关注**：若选 A，注意会触及 `interfaces/cli/src/cmd/arg_parser.rs`，与现有解析逻辑耦合。

> ✅ **提议默认（2026-10-01，D17 自主实现采纳，可覆盖）：方案 A — 基于 clap 派生补全。** 重构参数解析为 clap 并自动生成 bash/zsh/fish/pwsh 补全脚本。

## E. 测试与质量门禁

### D14. 覆盖率门槛与 SCA 工具怎么设？
**问题**：当前无覆盖率度量、无 `cargo audit`/`cargo deny`。要不要设门槛、引工具？
**背景**：审计列为 Medium 缺失。
**备选方案与后果**：
- **方案 A（推荐｜覆盖率门槛 + cargo audit）**：设最低覆盖率（如 60%）+ CI 引入 audit/deny。→ 质量与供应链安全双保障，CI 略增时。
- **方案 B（仅 cargo audit）**：先不做覆盖率门槛。→ 快速补安全短板。
- **方案 C（暂不设门槛）**：保持现状。→ 最快，但遗留风险。
**建议关注**：`cargo audit` 几乎零成本，建议无论如何先上。

> ✅ **已决策（2026-10-01）：方案 A — 覆盖率门槛（≥60%）+ CI 引入 cargo audit / cargo deny。** 质量与供应链安全双保障，写入发布门禁。

### D15. 桌面端 E2E 测什么框架？
**问题**：桌面端 E2E 完全缺失。用哪套做核心路径回归？
**背景**：PRD E7 列 Playwright E2E。
**备选方案与后果**：
- **方案 A（推荐｜Playwright）**：覆盖启动→对话→工具卡→审批。→ 生态成熟。
- **方案 B（自研 harness）**：基于现有 `client-core` 测试扩展。→ 贴合架构，但维护成本自担。
- **方案 C（暂以单测替代）**：先不做 E2E。→ Ga 可发，但回归保障弱。
**建议关注**：与 D8 范围联动——若首版走最小可用，E2E 可后置到 1.5.x。

> ✅ **提议默认（2026-10-01，D17 自主实现采纳，可覆盖）：方案 A — Playwright。** 覆盖启动→对话→工具卡→审批核心路径；随 D8 全量 P2 节奏落地。
