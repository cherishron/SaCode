# SaCode 改进规划方案

> 本方案基于《SaCode 可行性评估报告》（docs/report.md）四维评估结论制定。
> 报告核心结论：技术能力不输第二梯队，但界面覆盖（IDE 缺失）、首次体验门槛过高、定位模糊（工具 vs 平台双线推进）、部分过度设计（Loop 四层架构、知识 9 文件分类、五维冲突检测）是当前主要问题。
> 一句话战略：**停止平台化能力的深度投入（ACP/LSP/Daemon 扩展），把所有资源集中到三个最高 ROI 的事上——IDE 插件、国内 provider 零配置接入、首次使用体验优化。先让用户能用起来，再谈差异化。**

---

## 一、项目目标

### 1.1 总目标

把 SaCode 从"第二梯队尾部 / 第三梯队头部"提升到"国内开发者首选的终端 AI 编程工具"，形成清晰的产品叙事：

> **"Claude Code 的体验，国内模型原生适配，企业级可审计。"**

### 1.2 阶段性目标（按优先级）

| 阶段 | 目标 | 对应报告维度 |
|------|------|--------------|
| P0 — 体验闭环 | 首次使用体验打通：安装→配置→第一个任务≤3 分钟 | 维度四：首次体验断裂 |
| P1 — 界面补齐 | 上线 VSCode 扩展（最简调用 `sacode serve`），用户基数扩大 3-5 倍 | 维度一：界面覆盖严重不足 |
| P2 — 定位聚焦 | 明确为"面向国内开发者的终端 AI 编程工具"，砍掉/降级平台化深度投入 | 维度三：定位模糊 |
| P3 — 简化设计 | 砍掉 3 项过度设计（Loop 四层架构→轻量 /goal、知识 9 文件→3 文件、五维冲突→审批+拦截） | 维度二：过度设计 |
| P4 — 差异化强化 | 强化 3 项核心机制（三级执行模式、沙箱审计、checkpoint 恢复）作为企业决策因子 | 维度二：核心机制保留 |
| P5 — 场景补齐 | 补齐 4 个空白场景：CI/CD 集成、代码审查、远程开发、测试编写 | 维度四：使用场景覆盖不完整 |

### 1.3 量化目标

- 首次配置步骤从 4 步（/login→Base URL→API Key→/models→选择）降到 2 步（选择 provider→输入 Key）
- 界面覆盖从 1 类（CLI/TUI/REPL）扩展到 2 类（+ VSCode 插件）
- 命令体系从 40+ 子命令 + 20+ TUI 命令收敛为 5 个一级命令 + 按需发现的二级命令
- 内置 provider 预设：DeepSeek、通义千问、智谱 GLM、OpenAI、自定义
- 过度设计砍掉 3 项，核心机制强化 3 项

## 二、实施步骤

### 步骤 1 — 首次体验优化（P0，最高优先级）

**对应报告：** 维度四"首次使用体验断裂" + 维度一"模型兼容性差距"

1.1 重构 `/login` 为交互式选择流程：
```
sacode  →  检测到未配置 provider
         →  选择你的模型服务：
            1. DeepSeek（推荐，性价比最高）
            2. 通义千问
            3. 智谱 GLM
            4. OpenAI
            5. 自定义
         →  输入 API Key: ********
         →  ✅ 已配置，开始使用
```
- 把 "Base URL" 隐藏到"自定义"选项里，大多数用户不需要知道
- 预置 provider 模板（Base URL + 默认模型 + 显示名）

1.2 编写渐进式上手路径文档：
- 30 秒安装 → 1 分钟配置 → 3 分钟第一个任务 → 5 分钟进阶用法
- tutorials.md 改为 cheat sheet 风格的快速参考（当前太长太详细）

**涉及文件：**
- `interfaces/cli/src/cmd/config.rs` / `provider_config.rs`（provider 预设）
- `interfaces/cli/src/repl.rs` / `tui/bootstrap.rs`（首次启动引导）
- `docs/guides/getting-started.md` / `tutorials.md`（文档重写）

---

### 步骤 2 — VSCode 扩展开发（P1，ROI 最高单项投入）

**对应报告：** 维度一"界面覆盖严重不足" + 维度三调整建议"立即补齐 IDE 插件"

2.1 最简版 VSCode 扩展：
- 通过子进程调用 `sacode serve`（HTTP/SSE 端点已存在：`runtime/src/daemon/` 11 个 REST + SSE）
- 在 VSCode 侧边栏渲染对话面板，复用 SSE 事件流（`/api/stream`、`/events`）
- 第一版仅支持：发起任务、查看工具调用、显示结果，不做编辑器内联操作

2.2 后续迭代：
- 编辑器选区 → 上下文注入
- `sacode ide` 命令从"仅生成配置文件"升级为"安装/激活 VSCode 扩展"
- 评审审批流的 IDE 内可视化

**涉及文件：**
- 新增 `interfaces/vscode/` 目录（扩展工程）
- `interfaces/cli/src/cmd/ide.rs`（命令升级）

---

### 步骤 3 — 定位聚焦与平台化收敛（P2）

**对应报告：** 维度三"整体方向是否跑偏"

3.1 PRD 与文档定位调整：
- 明确定位为"面向国内开发者的终端 AI 编程工具"，平台化是结果不是起点
- 核心叙事统一为："Claude Code 的体验，国内模型原生适配，企业级可审计"
- 在 PRD 中显式声明国内市场定位（当前 PRD 完全未提及，但 MulanPSL 协议、国内搜索引擎、国产模型兼容已暗示）

3.2 砍掉/延后平台化深度投入：
- ACP（`interfaces/acp/`）：维持现状，不新增功能
- LSP（`interfaces/lsp/`）：维持现状，不新增功能
- Daemon：维持现有 11 端点用于 VSCode 扩展，不扩展新端点

3.3 资源重新分配：
- 从 ACP/LSP/Daemon 扩展释放的人力 → 投入 IDE 插件、provider 预设、代码库理解质量

**涉及文件：**
- `docs/product/PRD.md`（定位修订）
- `docs/product/roadmap.md`（路线图调整：明确 v1.0+ 平台能力维持现状）

---

### 步骤 4 — 简化过度设计（P3）

**对应报告：** 维度二"规则与约束的必要性审查"调整建议

4.1 Loop 四层自治架构 → 轻量 /goal：
- 当前：目标拆分→阶段状态机→结构化验收→成功停机（过重）
- 目标：`/goal <完成条件>` + 自动检测完成状态（对齐 Claude Code）
- 保留任务拆分能力，但去掉显式状态机和四层验收

4.2 知识系统 9 文件分类 → 合并为 3 个：
- `project.md`（事实+模块+命令）
- `experience.md`（pitfalls+workflows+decisions）
- `preferences.md`（偏好+策略）
- 迁移脚本：把现有 9 文件内容归并到 3 文件

4.3 五维冲突检测 → 简化为审批+拦截：
- 保留：`validation_conflict` 触发 `InterventionRequest`（审批闭环 + 危险命令拦截）
- 简化：不再维护完整的五维矩阵，聚焦"危险副作用拦截 + 用户审批"
- 故障转移路由从独立子系统降级为 provider 配置项

4.4 AutoLearner 调整：
- 保留"mistakes → candidate → 人工审核"闭环
- BM25 索引 + 衰减机制延后到知识量超过 100 条再引入

4.5 命名调整：
- `yolo` 模式重命名为对企业用户更严肃的名称（如 `auto` 或 `full`）

**涉及文件：**
- `runtime/src/agents/orchestrator.rs` / `summary_compactor.rs`（冲突简化）
- `runtime/src/memory/learner.rs` / `runtime/src/wiki/mod.rs`（知识文件合并）
- `interfaces/cli/src/cmd/orchestrator_entry.rs`（/goal 轻量化）
- `kernel/src/model/config.rs`（模式命名）

---

### 步骤 5 — 强化核心机制（P4）

**对应报告：** 维度二"保留并强化 3 项核心机制"

5.1 三级执行模式（plan/build/yolo）：
- 保留三级分级（比 Claude Code 的 plan/execute 两级更细，是真差异化）
- 在 TUI footer 强化视觉提示，让用户 30 秒内感知
- 命名调整见步骤 4.5

5.2 沙箱审计：
- `audit.log` 作为企业决策因子强化宣传
- 审计日志格式文档化，支持企业 SIEM 接入
- 审批流使用弹出式确认框（显示操作 + 影响范围 + 确认/拒绝）

5.3 checkpoint 恢复：
- 长任务可暂停、可恢复、可取消已落地，强化为产品卖点
- Loop 执行时在顶部显示阶段进度条（如 `Phase 2/5: 实现基础游戏循环 ●●○○○`）

**涉及文件：**
- `runtime/src/tools/sandbox_guard.rs`（审计强化）
- `interfaces/cli/src/tui/`（进度条、审批可视化）
- `runtime/src/agents/checkpoint.rs`（如存在）

---

### 步骤 6 — TUI 信息密度与交互增强（P4 伴生）

**对应报告：** 维度四"TUI 交互信息密度不足"

6.1 工具调用实时反馈：
- 对话流中插入工具调用的可折叠卡片（工具名、参数摘要、结果摘要、耗时）
- 显示"正在读取文件..."、"正在执行命令..."状态

6.2 审批流可视化：
- build 模式下弹出式确认框，显示影响范围

6.3 命令体系分层：
- 一级命令（用户必须知道 5 个）：`/login`、`/models`、`/mode`、`/agents`、`/help`
- 二级命令（按需发现）：`/memory`、`/wiki`、`/loop`、`/checkpoint`
- 三级命令（CLI 子命令）：其余全部归入 CLI，不在 TUI 暴露

6.4 `/help` 上下文感知：
- 根据当前模式（plan/build/yolo）显示相关命令

**涉及文件：**
- `interfaces/cli/src/tui/` 全部模块
- `interfaces/cli/src/repl.rs`

---

### 步骤 7 — 场景补齐（P5）

**对应报告：** 维度四"使用场景覆盖不完整"

按优先级补齐 4 个空白场景：

7.1 CI/CD 集成（Ghost 模式 + `--json` 输出已有基础）：
- 补齐 CI 脚本模板（GitHub Actions / GitLab CI）
- 文档：CI/CD 集成最佳实践

7.2 代码审查场景：
- `/review-pr` skill 已有，增强为对 diff 做结构化审查
- 输出：变更影响面、风险点、建议

7.3 远程开发场景：
- SSH 连接后 `sacode` 直接可用，确保终端兼容性
- 文档：远程开发使用指南

7.4 测试编写场景：
- 结合 `test.run` 工具，提供"分析代码→生成测试→运行验证"一键流程
- 支持 cargo / npm / go / pytest 框架自动检测（已有）

**涉及文件：**
- `docs/guides/tutorials.md` / `examples.md`（场景文档）
- `runtime/src/tools/test/runner.rs`（测试流程）
- `skills/` 目录（新增/增强 skill）

### 步骤 8 — 开源策略调整（伴随性）

**对应报告：** 维度一"开源生态差距" + 维度三调整建议

8.1 评估协议调整：
- 考虑核心 runtime 改为 MIT/Apache-2.0
- 保留企业版功能（沙箱审计、Daemon 管理）作为增值

8.2 npm 包策略评估：
- 当前预编译二进制分发，非源码即用
- 评估是否提供源码构建路径

**涉及文件：**
- `LICENSE`（协议变更需法律审查）
- `README.md` / `docs/README.md`（生态说明）
- `npm-package/`（分发策略）

## 五、风险分析与应对措施

### 风险 1 — VSCode 扩展工程复杂度超预期

- **影响：** 阶段 2 延期，影响整体里程碑
- **概率：** 中
- **应对：**
  - 严格控制 MVP 范围：第一版仅"发任务 + 看结果"，不做编辑器内联操作
  - 复用现有 `sacode serve` 端点，避免后端重写
  - 如延期超 1 周，降级为"生成 VSCode 配置 + 外部终端唤起"过渡方案

### 风险 2 — 过度设计简化引发回归

- **影响：** /goal 轻量化、知识文件合并、冲突检测简化可能破坏现有功能
- **概率：** 中高
- **应对：**
  - 每项简化前先补充测试覆盖（`cargo test --workspace`）
  - 知识文件合并提供迁移脚本，保留原文件备份
  - 冲突检测简化保留 `validation_conflict` → `InterventionRequest` 主路径，只删冗余维度
  - 阶段 4 末做全量回归

### 风险 3 — 定位调整引发现有用户/文档不一致

- **影响：** PRD/roadmap/README 表述不一致（已知 roadmap.md 第 86 行与第 119 行存在冲突）
- **概率：** 高
- **应对：**
  - 阶段 3 集中做文档一致性审查
  - 建立"文档真相源"清单：以 `Cargo.toml`、`.github/workflows/*`、`scripts/check-release.js` 为准
  - 所有文档头部标注最后更新日期

### 风险 4 — 开源协议变更法律风险

- **影响：** MulanPSL-2.0 → MIT/Apache-2.0 可能涉及既有贡献者授权
- **概率：** 中
- **应对：**
  - 阶段 6 仅做评估，不强制变更
  - 如法律审查不通过，保留 MulanPSL 但补充英文说明 + 商业授权选项

### 风险 5 — 单人/小团队资源瓶颈

- **影响：** 12 周计划可能延期
- **概率：** 高
- **应对：**
  - 严格按优先级推进：P0（体验）→ P1（IDE）→ P2（定位）→ P3（简化）→ P4（强化）→ P5（场景）
  - 每阶段末评估，如延期则 P5 场景补齐可延后到下个周期
  - 平台化收敛（ACP/LSP/Daemon 不扩展）本身即释放资源

### 风险 6 — 国内 provider API 差异导致预设不准

- **影响：** provider 预设模板与实际 API 不符
- **概率：** 中
- **应对：**
  - 每个预设配置一个测试账号实际联调
  - 预设模板支持版本号，后续可热更新
