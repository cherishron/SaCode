# SaCode 场景教程

本文档按真实开发场景组织，帮助你把 SaCode 用到“能解决问题”的程度，而不是只停留在命令记忆层。

## 1. 理解一个陌生仓库

### 目标
快速弄清楚入口、分层、主要模块和高风险区域，建立整体认知

### 场景背景
你刚刚接手一个新项目，或者需要快速了解一个开源仓库的结构和设计，希望在短时间内掌握核心内容，避免盲目探索。

### 完整步骤

#### 步骤 1：启动 SaCode 并配置环境

```bash
# 进入项目目录
cd /path/to/unknown-project

# 启动 SaCode
sacode
```

**配置 Provider（如果首次使用）**：
```text
/login
Base URL: https://api.openai.com/v1
API Key: sk-xxxxxxxxxxxxxxxxxxxxxxxx
Provider name (optional): my-openai
```

**选择模型**：
```text
/models
# 选择适合代码分析的模型，如 gpt-4 或 deepseek-coder
```

#### 步骤 2：获取整体概览

**输入任务**：
```text
解释这个仓库的主要分层、真实入口和高风险模块
```

**预期输出**：
- 项目的整体架构图
- 主要分层和模块职责
- 真实入口点（不是测试入口）
- 高风险或复杂的模块
- 推荐的深入阅读顺序

**如果输出不够详细**：
```text
先读 Cargo.toml、README.md、CI 配置文件和主入口，再详细解释这个仓库如何运行
```

#### 步骤 3：深入了解关键模块

**针对特定模块询问**：
```text
详细说明 kernel、runtime、interfaces/cli 的职责边界和它们之间的依赖关系
```

**继续追问**：
```text
这个仓库中，哪些文件是真正的入口点？哪些测试入口不参与实际运行？
```

**了解数据流**：
```text
从用户输入到最终输出，这个项目的主要数据流是什么样的？涉及哪些关键模块？
```

#### 步骤 4：识别关键路径和风险点

**找出关键路径**：
```text
这个仓库最重要的代码路径是什么？如果只读 5 个文件，应该读哪 5 个？
```

**识别风险区域**：
```text
哪些模块最容易出问题？如果要做回归测试，应该优先关注哪些地方？
```

**了解测试覆盖**：
```text
这个仓库的测试覆盖情况如何？哪些核心功能缺少测试？
```

#### 步骤 5：建立工作理解

**了解开发流程**：
```text
这个仓库的开发验证顺序是什么？从修改代码到发布，需要经过哪些步骤？
```

**了解协作约束**：
```text
基于 AGENTS.md，这个项目有哪些重要的协作约束和约定？
```

**了解代码风格**：
```text
这个项目遵循什么代码风格和规范？有哪些特殊的约定需要遵守？
```

#### 步骤 6：记录重要发现

**添加到记忆**：
```text
/memory append 这个仓库的入口在 interfaces/cli/src/cmd/mod.rs，核心逻辑在 runtime/src/agents/ --type memory
```

**记录工作流程**：
```text
/memory append 开发验证顺序：cargo test -> cargo build -> npm run check-release --type workflow
```

**记录重要决策**：
```text
/memory append 项目采用分层架构：kernel(纯逻辑) -> runtime(副作用) -> interfaces(交互层) --type decision
```

### 常见问题和解决方案

#### 问题 1：输出太泛泛，不够深入

**解决方案**：
- 明确要求先读关键文件
- 指定具体的分析角度
- 要求给出具体的文件路径和代码位置

**示例**：
```text
不要泛泛而谈，先读 runtime/src/agents/model_router.rs 的具体实现，再解释模型路由逻辑
```

#### 问题 2：不相关内容太多

**解决方案**：
- 明确分析范围
- 排除不关心的部分
- 要求聚焦核心内容

**示例**：
```text
只关注业务逻辑，忽略测试代码、文档和示例代码
```

#### 问题 3：缺少实际例子

**解决方案**：
- 要求提供具体代码片段
- 要求给出实际调用链
- 要求展示数据流示例

**示例**：
```text
给我一个具体的请求从进入到响应的完整调用链，包括关键的函数调用和数据传递
```

## 2. 定位问题和回归

### 目标
找到最可能的失败点，并给出最短修复路径

### 场景背景
你刚刚修改了代码，发现测试失败了，或者接到 bug 报告需要快速定位问题根源。你希望找到最可能的问题位置，并给出高效的修复方案。

### 完整步骤

#### 步骤 1：启动诊断

**检查当前状态**：
```bash
cd /your/project
sacode doctor
```

**查看当前改动**：
```bash
git status
git diff --stat
```

#### 步骤 2：让 SaCode 做初步分析

**输入任务**：
```text
定位当前仓库里最可能导致测试失败或回归的问题
```

**预期输出**：
- 最可能的问题位置
- 问题类型分析（逻辑错误、配置问题、依赖问题等）
- 修复优先级排序
- 初步修复建议

**如果输出不够具体**：
```text
只关注最近 3 次提交的改动，分析最可能的问题点
```

#### 步骤 3：结合当前 diff 分析

**查看具体改动**：
```bash
git diff HEAD~3 | sacode "根据这份改动判断最可能的回归风险和验证顺序"
```

**预期输出**：
- 改动影响范围分析
- 潜在回归点识别
- 建议的验证顺序
- 风险等级评估

**如果改动很大**：
```bash
git diff HEAD~3 --name-only | sacode "分析这些文件的改动，找出最容易出问题的地方"
```

#### 步骤 4：获取验证路径

**输入任务**：
```text
针对这个仓库给我一个最省时的验证顺序，先跑最值钱的检查
```

**预期输出**：
- 验证步骤优先级排序
- 每个步骤的目的和预期结果
- 何时停止验证的判断标准
- 失败时的后续行动

**示例输出**：
```
验证顺序：
1. 编译检查（5分钟）- 确保代码能编译
2. 单元测试（10分钟）- 快速发现逻辑错误
3. 集成测试（15分钟）- 验证模块间交互
4. 端到端测试（20分钟）- 验证完整流程

如果第 2 步失败，跳到第 5 步：查看具体失败信息
```

#### 步骤 5：缩小问题范围

**如果知道任务范围，指定具体模块**：
```text
只看 runtime 相关改动，帮我判断先跑哪些 sacode-runtime 测试
```

**更精确的范围限定**：
```text
只关注 runtime/src/agents/ 目录下的改动，分析可能的影响面
```

**针对特定功能**：
```text
只分析模型路由相关的改动，判断是否有回归风险
```

#### 步骤 6：深入问题分析

**获取具体错误信息**：
```bash
# 运行测试
cargo test --workspace 2>&1 | tee test-output.log

# 分析错误
cat test-output.log | sacode "分析这些测试错误，找出根本原因"
```

**如果错误信息不明确**：
```text
基于测试失败的症状，分析最可能的代码问题位置和原因
```

#### 步骤 7：生成修复方案

**输入任务**：
```text
针对这个问题给出最小可行修复路径，尽量少改文件，避免引入新问题
```

**预期输出**：
- 具体的修复方案
- 需要修改的文件和代码位置
- 修复的验证方法
- 潜在的副作用

**如果需要多种方案**：
```text
给出 2-3 个修复方案，分别说明优缺点和推荐选择
```

#### 步骤 8：执行修复

**使用 build 模式执行修复**：
```bash
sacode "修复刚才分析的问题" --mode build
```

**执行过程中的决策**：
- 询问是否修改文件：仔细审查修改内容
- 询问是否运行测试：确认测试范围
- 询问是否提交：验证修复效果

#### 步骤 9：验证修复

**运行相关测试**：
```bash
# 运行失败的具体测试
cargo test <test_name>

# 运行相关模块测试
cargo test -p <package_name>

# 运行完整测试
cargo test --workspace
```

**如果还有问题**：
```text
修复后仍有问题，继续分析剩余的错误
```

#### 步骤 10：总结经验

**记录问题和解决方案**：
```text
/memory append "问题：[问题描述]，解决方案：[解决方案]，避免方法：[如何避免]" --type memory
```

**更新错题本**：
```text
/mistakes add "这次遇到的问题描述和解决过程"
```

### 问题定位技巧

#### 技巧 1：二分法定位

**方法**：使用 git bisect 快速定位引入问题的提交

```bash
# 开始二分
git bisect start

# 标记当前提交为 bad
git bisect bad HEAD

# 标记已知正常的提交为 good
git bisect good <good-commit-hash>

# 自动测试
git bisect run cargo test
```

#### 技巧 2：增量验证

**方法**：逐步扩大测试范围，快速定位问题

```bash
# 先编译
cargo build

# 再运行单元测试
cargo test --lib

# 然后运行集成测试
cargo test --test '*'

# 最后运行完整测试
cargo test --workspace
```

#### 技巧 3：日志分析

**方法**：通过日志定位问题

```bash
# 启用详细日志
RUST_LOG=debug cargo test 2>&1 | tee debug.log

# 分析日志
cat debug.log | sacode "从这些日志中找出问题的关键信息"
```

#### 技巧 4：依赖分析

**方法**：分析依赖变化导致的问题

```bash
# 查看依赖变化
cargo tree -d

# 分析影响
cargo tree -d | sacode "分析这些依赖变化可能带来的问题"
```

### 常见问题模式

#### 模式 1：空指针解引用

**症状**：程序崩溃，错误信息涉及 null/None

**分析步骤**：
1. 找出解引用的位置
2. 追溯变量来源
3. 检查是否正确处理了 None 情况
4. 添加适当的错误处理

#### 模式 2：类型不匹配

**症状**：编译错误，类型不匹配

**分析步骤**：
1. 识别期望的类型
2. 找出实际提供的类型
3. 理解类型转换规则
4. 添加适当的类型转换

#### 模式 3：竞态条件

**症状**：间歇性失败，难以重现

**分析步骤**：
1. 识别共享状态
2. 找出并发访问点
3. 检查同步机制
4. 添加适当的锁或原子操作

#### 模式 4：资源泄漏

**症状**：内存占用持续增长，性能下降

**分析步骤**：
1. 使用内存分析工具
2. 识别泄漏的资源
3. 找出分配未释放的代码
4. 添加适当的资源释放逻辑

## 3. 做一次受控改动

### 目标
让 SaCode 改代码，但保持可控，确保安全性和质量

### 场景背景
你需要修改代码，但希望保持对修改过程的完全控制，避免意外修改或引入新问题。你希望在修改的每个关键节点都能审查和确认。

### 完整步骤

#### 步骤 1：明确改动的性质和范围

**评估改动类型**：
```text
分析这个任务的性质：是 bug 修复、功能添加、还是重构？风险程度如何？
```

**确定改动范围**：
```text
这个改动会影响哪些文件和模块？是否有潜在的副作用？
```

#### 步骤 2：选择合适的执行模式

**根据任务性质选择模式**：

**plan 模式**（适合复杂任务）：
```bash
sacode "设计一套改进 AGENTS.md 生成流程的方案" --mode plan
```

**使用场景**：
- 任务复杂，影响范围大
- 不确定实现方案
- 需要先了解全貌
- 需要多种方案比较

**build 模式**（适合常规修改）：
```bash
sacode "修复当前 TUI 中与 /models 相关的交互问题" --mode build
```

**使用场景**：
- 明确的 bug 修复
- 小规模功能添加
- 已知实现方案的任务
- 需要保持控制的修改

**yolo 模式**（适合高确定性任务）：
```bash
sacode "批量整理这个仓库的 Markdown 文档标题层级" --mode yolo
```

**使用场景**：
- 格式化、重构等确定性任务
- 范围明确，风险低
- 批量处理操作
- 已验证的自动化任务

#### 步骤 3：使用 plan 模式做规划（推荐）

**输入规划任务**：
```text
为我设计一个改进 TUI 任务状态流转的方案，包括任务拆解、影响分析和验证建议
```

**预期输出**：
- 详细的任务拆解
- 需要修改的文件列表
- 影响范围分析
- 多个实现方案比较
- 推荐方案和理由
- 验证建议

**审查规划结果**：
```text
这个规划是否合理？有没有遗漏的地方？有没有更好的实现方式？
```

**继续完善规划**：
```text
基于刚才的分析，给我更详细的实现步骤，包括具体的代码位置和修改内容
```

#### 步骤 4：使用 build 模式执行修改

**输入修改任务**：
```bash
sacode "修复 TUI 中 /models 选择后 provider 和 model 不同步的问题" --mode build
```

**执行过程中的控制点**：

**控制点 1：分析阶段**
- SaCode 分析问题，给出初步方案
- 你审查方案是否合理
- 可以要求调整方案或给出替代方案

**控制点 2：文件选择**
- SaCode 提出要修改的文件列表
- 你确认是否修改这些文件
- 可以要求添加或排除某些文件

**控制点 3：代码修改**
- SaCode 展示具体的代码修改
- 你仔细审查每个修改
- 可以接受、拒绝或要求调整

**控制点 4：测试验证**
- SaCode 建议运行哪些测试
- 你确认测试范围
- 可以要求额外的测试

**控制点 5：最终确认**
- SaCode 总结所有修改
- 你确认是否提交
- 可以要求进一步修改

#### 步骤 5：监控执行过程

**实时监控**：
- 关注 SaCode 的输出
- 检查每个修改的合理性
- 及时提出疑问或要求调整

**质量检查**：
```text
审查刚才的修改，检查是否有：1. 逻辑错误 2. 性能问题 3. 安全隐患 4. 代码风格问题
```

**风险控制**：
```text
这些修改是否有潜在风险？是否需要额外的保护措施？
```

#### 步骤 6：验证修改效果

**运行相关测试**：
```bash
# 运行单元测试
cargo test -p sacode-cli

# 运行集成测试
cargo test --test '*'

# 运行完整测试
cargo test --workspace
```

**功能验证**：
```text
手动测试修改的功能，确认是否按预期工作
```

**性能检查**：
```text
检查修改是否影响了性能，必要时进行性能测试
```

#### 步骤 7：审查最终结果

**查看最终修改**：
```bash
git diff
```

**要求 SaCode 审查**：
```text
审查这次修改，检查是否：1. 完整解决了问题 2. 没有引入新问题 3. 代码质量良好 4. 符合项目规范
```

**生成提交说明**：
```bash
git diff | sacode "根据改动生成一条简洁准确的 commit message"
```

### 控制策略

#### 策略 1：增量修改

**方法**：将大任务拆分成小步骤，逐步完成

**示例**：
```text
这个任务太大，先完成第一步，等我确认后再继续下一步
```

#### 策略 2：分支保护

**方法**：在新分支上进行修改，确认后再合并

```bash
# 创建新分支
git checkout -b fix/issue-123

# 执行修改
sacode "修复 issue" --mode build

# 验证后合并
git checkout main
git merge fix/issue-123
```

#### 策略 3：审查每个修改

**方法**：对每个代码修改都进行详细审查

**示例**：
```text
详细解释这个修改的目的和影响，我不理解的部分请说明
```

#### 策略 4：快速回滚

**方法**：保留回滚能力，出现问题能快速恢复

```bash
# 修改前创建备份
git stash

# 执行修改
sacode "修改任务" --mode build

# 如果有问题，快速回滚
git stash pop
```

### 风险管理

#### 风险识别

**常见风险**：
- 修改范围过大，难以控制
- 引入新的 bug
- 性能下降
- 兼容性问题
- 安全漏洞

**风险识别方法**：
```text
分析这个修改可能带来哪些风险？如何避免这些风险？
```

#### 风险缓解

**缓解策略**：
1. **小步修改**：将大任务拆分成小步骤
2. **充分测试**：在每个步骤后进行充分测试
3. **代码审查**：仔细审查每个修改
4. **备份恢复**：保留回滚能力
5. **渐进发布**：先在小范围测试，再逐步推广

#### 应急预案

**回滚计划**：
```bash
# 快速回滚到修改前
git reset --hard HEAD~1
```

**修复计划**：
```text
如果修改后出现问题，给我紧急修复方案
```

### 最佳实践

#### 实践 1：先规划后执行

**原因**：充分的规划可以避免很多问题

**方法**：
1. 使用 plan 模式充分了解任务
2. 审查规划的合理性
3. 确认后再开始执行

#### 实践 2：保持小步快跑

**原因**：小步修改更容易控制和回滚

**方法**：
1. 将大任务拆分成小步骤
2. 每步完成后验证
3. 确认无误后再进行下一步

#### 实践 3：充分测试

**原因**：测试可以及早发现问题

**方法**：
1. 在每个修改后运行相关测试
2. 进行手动测试验证功能
3. 必要时进行性能测试

#### 实践 4：详细记录

**原因**：记录可以帮助回顾和总结

**方法**：
1. 记录每个修改的目的和影响
2. 记录遇到的问题和解决方案
3. 记录经验教训

### 后续改进

**代码审查**：
```text
这次修改有哪些可以改进的地方？有没有更好的实现方式？
```

**文档更新**：
```text
根据这次修改，更新相关文档
```

**经验总结**：
```text
/memory append "这次修改的经验：[经验总结]" --type memory
```

通过这个受控改动的流程，你可以安全地修改代码，同时保持对整个过程的完全控制，确保修改的质量和安全性。

## 4. 用 TUI 跑多轮任务

目标：在一个会话里连续做分析、修改、验证和追问。

### 关键快捷键

- `Ctrl+Q`：退出
- `Esc`：清空输入或取消当前执行
- `Ctrl+T`：开启或关闭思考功能
- `Ctrl+M`：切换 `plan` / `build` / `yolo`

### 常用命令

- `/connect`：快速接入 Provider
- `/models`：选择模型
- `/doctor`：检查配置是否就绪
- `/status`：查看 MCP 与插件状态
- `/memory`：查看或写入分类记忆
- `/wiki`：查看知识库加载状态
- `/loop <task>`：循环执行直到完成或熔断
- `/cancel`：取消当前任务

### 典型流程

1. `/doctor`
2. `/models`
3. 提交任务
4. 根据输出继续追问
5. 用 `/memory append ...` 记录稳定结论
