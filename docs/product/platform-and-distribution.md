# SaCode 平台支持与分发要求

- 决策日期：2026-10-13。
- 性质：用户确认的产品目标与验收要求，不是全平台已实现或发布声明。
- 功能范围以 [PRD](PRD.md) 的 F01–F21 为准；本文细化 F20 的平台、构建与分发，不缩减其他能力域。

## 1. 产品定位与入口

SaCode 是面向开发者的**可信、可控的 AI 编程工作台**，不是以 DSH 全系统复刻或消除编译警告为目标的实验。

仓颉 `core` 是共享业务实现：会话与执行事实、授权、取消、恢复及结算保持统一。CLI、Host、daemon 和前端适配这份核心，不为不同平台复制 Agent 主循环或授权规则。会话日志是会话与执行事实的真源；文件、Git、数据库、配置等仍有各自的权威源，不把所有业务数据强塞进日志。

- **CLI**：独立终端入口，不依赖 Electron 桌面进程。
- **Host**：供桌面调用的仓颉协议宿主，不是另一份业务核心；必须在各桌面目标平台构建和运行。
- **daemon / 服务端**：仓颉服务入口，远程连接、身份与会话归属独立验收；不因能编译就宣称远程任务可用。
- **Electron 桌面**：Windows、Linux、macOS 的工作台前端。
- **鸿蒙前端**：后续独立的 ArkTS/ArkUI 项目接入共享业务能力，不要求 Electron 或 electron-builder 输出鸿蒙安装包。具体嵌入或通信方式待单独设计，不预设只走远程连接。

“双入口”仅指 CLI 与桌面的用户交互形态，不代表系统只有两个可执行模块。

## 2. 目标平台矩阵

| 平台 | CLI | daemon / 服务能力 | 工作台前端 | 验收边界 |
| --- | --- | --- | --- | --- |
| Windows | 必须支持 | 必须支持 | Electron，必须支持 | 按架构验证构建、安装、真实任务与恢复 |
| Linux | 必须支持 | 必须支持 | Electron，必须支持 | 有用户提供的 Linux 环境；不是永久停在“可编译” |
| macOS | 必须支持 | 必须支持 | Electron，必须支持 | 当前缺目标设备运行证据；可先建设构建与打包，运行验收待环境，不删目标 |
| 鸿蒙 / OHOS 目标环境 | 必须支持，保留在范围内 | 共享服务能力保留，独立常驻 daemon 的部署条件待核 | 后续独立 ArkTS/ArkUI 项目 | 当前无设备；工具链、可执行文件及权限边界须核实，未验证不能宣传为可用 |

鸿蒙 CLI 的初始部署目标是**具有终端或 shell 执行条件的目标环境**。OpenHarmony 的开发/调试环境和普通 HarmonyOS 应用沙箱不是同一权限环境；SDK 同源不证明任意子进程、Git、Node、ACP Agent 或语言服务器都能运行。后续前端接入也不能继承调试 shell 权限。

Windows/Linux/macOS 的 x64、arm64，以及 OHOS 的 arm64/x64 均按实际工具链和产物逐项登记。当前只有部分架构的证据，不因存在 SDK 资产推导所有架构已支持；首批发行架构与最低系统版本在实施时冻结。

## 4. 平台后端要求

跨平台不只是给 electron-builder 加目标。核心和壳层必须满足以下契约：

1. **文件与持久发布**：观察版本、创建不覆盖、原子替换、持久追加及失败恢复有等价保证；原子可见性和断电持久性分别说明，不拿普通写文件替代持久屏障。
2. **进程身份与监督**：区分 alive / dead / unknown，无法查询不能当死亡；取消、超时和退出结果独立，处理自有进程及其获准子进程，不误杀其他会话。
3. **系统中断与协作式取消**：各平台真实接入；POSIX 信号回调不能照搬 Windows 的加锁遍历，需按异步信号安全约束设计。
4. **执行授权与隔离**：页面、CLI、MCP、PTC 和 ACP 适用动作进入共享授权/取消/结算链；worktree 是修改隔离，不等于 OS 安全沙箱。所需强制边界不可用时明确拒绝，不能静默裸跑。
5. **路径与数据根**：正确处理大小写、URI、符号链接、可执行名、权限和安装目录；打包态 Host 仍由绝对 resourcesPath 定位，不回退 asar。可写数据目录按平台规则与用户选择确定，不把 Windows 的 exe 旁存储机械复制到 macOS/Linux。
6. **运行依赖**：目标运行库、stdx、TLS 信任锚及实际需要的 Git/Node/语言服务器逐项处理；无 SDK 交付不是假装所有外部工具已存在。
7. **专项能力**：电脑控制、PTY、凭据存储、LSP 和外部 Agent 按目标平台与权限分别验收，不因业务契约共享推导系统能力相同。

Linux/macOS/OHOS 可以复用经验证的原生适配部分，但须保留 ABI、系统 API、加载器和权限差异；不承诺一份未经实测的 POSIX 实现直接覆盖三者。

## 5. CLI 与桌面分发

### 5.1 CLI 安装

- npm 是 Windows/Linux/macOS CLI 的主要便捷安装渠道：薄启动包按平台/架构选择对应原生产物包，不依赖桌面进程。
- 当前源码主包是 `npm/sacode-cli`（包名 `@stand-alone/sacode`），现有平台包为 `npm/sacode-cli-win32-x64`；其他平台包尚待实现/验证，不在本文宣称已发布。
- 主包、平台包、CLI、daemon、运行库与扩展宿主版本需一致或明确声明兼容，不把本机能启动代替 registry 安装验收。
- 同时提供适合目标环境的 release 压缩包及校验和，避免强制用户安装 npm 才能获得原生 CLI。其他通用安装渠道按实际需求接入，不自动新增未确认的包管理器方案。
- 鸿蒙 CLI 保留独立原生产物分发；npm/其他渠道在目标设备上的可用性待核，不笼统宣称“有 npm”或“没有 npm”。

### 5.2 桌面与服务包

- Electron 的 Windows/Linux/macOS 目标分别配套**同平台、同架构**的 Host、运行库、资源与加载路径；不能只改安装包后缀或搬用 Windows DLL。
- 安装格式、签名、公证、更新策略和最低系统版本按平台冻结。构建成功、能安装、能默认启动和真实任务通过分别记录。
- 完整服务包若包含 CLI、Host、daemon 与扩展宿主，应逐角色验证；只验 CLI/daemon 不可称整包通过。
- 鸿蒙前端独立应用包后续设计，不使用 Electron 平台目标代替。

## 6. GitHub 构建与产物要求

GitHub Actions 构建、打包并提供可下载产物是已确认目标。2026-10-14 本批新增 Windows/Linux/macOS 候选 workflow 与 OHOS 手动 self-hosted 交叉构建 workflow，**尚无实际 Actions 运行结果**；Git 远端仍是 Gitee，不能把 YAML 存在当成流水线已执行。步骤见 [构建指南](../build-platforms.md)。

- 所有产物关联固定提交 SHA、平台、架构、工具链版本、依赖版本、构建参数、校验和及验证日志；不同构建不能混用同名旧文件。
- Windows/Linux/macOS 优先使用对应构建环境；OHOS 在匹配 SDK 的构建机交叉构建，不能只传一个 `--target` 就认为具备完整工具链。
- 依赖准备必须可复现，不使用开发者绝对路径、不提交 SDK 二进制，不以 `.deps` 本机存在替代 runner 的安装步骤。
- 构建矩阵按“平台 × 架构 × 交付角色”明确必需成员：桌面平台包括 Host；鸿蒙角色依其独立前端方案，不机械要求 Electron。
- 自动化验收必须反映实际结果：失败为 FAIL，缺工具链/设备为 BLOCKED 或待验证；跳过不填 PASS。未验证产物可作为明确标识的构建候选，不宣传完整运行支持。
- CI 产物上传、GitHub Release 和 npm 正式发布是不同动作；仓库同步、发布凭据、签名与正式发布按独立授权处理，不因本要求自动推送到新远端或发布 npm。

## 7. 实施顺序与并发边界

两条线推进，但保持共享契约和文件归属，不以平台工作打断当前真实任务交付：

| 工作线 | 当前职责 | 边界 |
| --- | --- | --- |
| codex 入口与交付线 | 共享执行服务接入真实入口，页面工具的核心授权/取消/结算；ACP 真实委派、LSP 真实结果进入工作台；从验收源码统一重建 Host、CLI、桌面并验证默认启动/安装后任务 | 不用核心单测或契约登记代替实际工作台结果 |
| 平台与文档线 | 明确平台支持、工具链与分发边界，按确认的契约收口平台后端 | 最初仅授权文档；2026-10-14 已获平台代码及公共文件收口授权，具体范围见下方补记 |

2026-10-14 用户进一步授权：当前只有本会话工作，可以修改已有在途文件并按批提交/推送；本批实现平台后端、Linux 桌面路径/包目标、npm 与 GitHub 构建，codex 后续按提交记录复核再继续入口业务。该授权不等于把全部未完成 UI、旧测试或斜杠骨架一次性提交，也不授权正式 npm 发布。

依赖顺序是：工具链与平台契约 → 目标入口构建/启动/真实任务 → 壳层适配与完整打包 → 干净环境安装验收。CI 框架可并行建设，但不能替代前面各层验收。

macOS 与鸿蒙当前无设备不等于永久移出范围；先准备工具链、适配与构建证据，真实运行明确待验。警告清理、证据数量和历史 DSH 模块计数都不是交付主目标。
